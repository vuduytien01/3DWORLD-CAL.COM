# TS/JS Browser 3D in 2025-2026: can it carry a hospital-building visualization?

Date: 2026-11-06. Track: TS/JS / Web GPU landscape for a 2-person capstone (Next.js + Docker + AI guide). Target scene: isometric hospital map first, light first-person walkthrough later, on ordinary laptop iGPUs.

Every load-bearing claim is labeled **[measured]** (a published number with hardware and limiter stated), **[inferred]** (derived from cited measurements), or **[guess]** (no direct source; stated as judgment).

---

## Executive answer (10 lines)

1. Yes, TS/JS carries a hospital visualization comfortably: a few hundred draw calls and low-millions of triangles is a mid-tier workload for three.js on an iGPU. **[inferred from measured draw-call costs below]**
2. Use three.js (r186/r187, MIT, ~116K GitHub stars, tens of millions of weekly npm downloads) or, for React codebases, React Three Fiber v9 + drei on top of it. **[measured, npm/GitHub]**
3. Babylon.js 8/9 (Apache-2.0) is the batteries-included alternative: first-party physics, GUI, inspector, WebGPU since 5.0 with native WGSL shaders since 8.0. **[measured, official docs]**
4. WebGPU shipped in all four major engines by Nov 2025 (Chrome/Edge 113+, Firefox 141 Windows, Safari 26); caniuse puts support+partial at ~86-89% of global traffic. **[measured, web.dev + caniuse]**
5. Neither major lib defaults you into trouble: three.js `WebGPURenderer` auto-falls back to WebGL 2, Babylon ships `EngineFactory` doing the same. **[measured, official docs]**
6. WebGPU's real win is CPU-side draw-call cost, not pixels: in the same test scene, three.js spent 0.89-2.10 us/draw on WebGL2 vs 2.10-4.68 us on WebGPU on desktop Chrome (Babylon 2.35-4.83 vs 4.40-7.34). **[measured, community harness, public code]**
7. Practical budget for your scene: R3F's own docs say keep unbatched draw calls to "a few hundred or less, 1000 max"; instancing takes repeated furniture (beds, seats, doors) to hundreds of thousands of objects in one call. **[measured/inferred, official docs]**
8. WASM already does the heavy lifting invisibly: meshopt decodes at 1-3 GB/s (SIMD) from a ~32 KB module, KTX2 textures stay compressed in GPU memory (4-8x less VRAM), so asset pipelines are solved. **[measured, official READMEs]**
9. Ceiling on an Iris Xe-class iGPU at 1080p: ~60 fps with <300 draw calls and up to roughly 5-10M triangles if assets are compressed and floors are tiled; past ~3-5K material-switching draw calls any browser drops below 60 fps. **[inferred/guess, see limits section]**
10. Recommendation: build the isometric map with three.js + R3F on WebGL2-first (or `WebGPURenderer` with fallback), keep scene-graph discipline (instancing, per-floor tiles, LOD); a C++ renderer would buy GPU throughput you will not need at this scene size and cost you the entire web integration path. **[inferred]**

## What limits each number (benchmark provenance)

- **Per-draw-call CPU cost table (0.43-9.25 us).** `web-engines-compare`, results dated 2026-10-01, Chrome 154, 1K-20K boxes cloned from 100 meshes, 100 PBR materials, 1 directional light with shadow, 2 draws per box. Author: Martin Valigursky, a PlayCanvas engineer (so Babylon/three numbers come from a competitor's harness - read relatively, and his Babylon adapter used plain defaults). Machines: M4 Max, i7-10700F (GPU unspecified - do not read it as an iGPU result), Pixel 8 Pro. Limiter: pure CPU-side draw submission; GPU time excluded. https://forum.babylonjs.com/t/webgpu-cpu-cost-per-draw-call-in-9-29-9-30-and-which-small-prs-would-you-welcome/64298 **[measured]**
- **Independent cross-check:** endel/webgpu-webgl-benchmarks, 5,000 separately animated meshes, Chrome 151, M1 Pro: 12 ms CPU/frame (PlayCanvas), 24 ms (Babylon 9.26), 29 ms (three r186) on WebGPU. Same ranking, so the ordering is robust. **[measured]**
- **"WebGPU is faster" claim, bounded.** csarko.sh (Sep 2026) ported a real Babylon.js game ("Day Hike") to WebGPU on Apple M4 / Chrome 153: 1.53 ms/frame saved at native 2.4 Mpx, 9.93 ms at 9.7 Mpx - and the frame was GPU-limited (3.79 ms JS of 24.2 ms), so CPU savings barely showed. Conclusion: WebGPU wins grow with resolution and draw count; on a GPU-bound iGPU scene the backend switch alone buys little. https://csarko.sh/research/webgpu-vs-webgl2 **[measured]**
- **Counter-example that keeps you honest:** a WebGPU-first three.js project (dark-strands) measured WebGL2 ~2x faster (120 vs 60-70 fps) - not because of the backend, but because their code throttled the 870-draw shadow pass only on WebGL2. Limiter: application logic, not the API. https://github.com/VictorZakharov/dark-strands/pull/26 **[measured]**
- **Instancing win (60x).** spareilleux.github.io three.js course measurement, WebGPU backend, RTX 5080: 10,000 separate meshes = 10.3 ms CPU/frame vs one InstancedMesh of the same 800K triangles = 0.16 ms. Limiter: CPU scene-graph bookkeeping, GPU idle-ish; single-machine run. https://spareilleux.github.io/learn/threejs/08-performance-instancing-batching-lod/ **[measured]**
- **Absolute ceiling probe:** three.js forum plant benchmark (240 desktop samples, mixed hardware), 100K plants x 6,056 tris = 605.6M triangles/frame: ~20 fps on all three backends. 1K/10K rows hit vsync (60 fps). Limiter: GPU triangle throughput; stress fixture, not a budget. https://discourse.threejs.org/t/three-js-plant-instancing-benchmark-240-desktop-samples-csv-json-and-a-standalone-harness/95719 **[measured]**
- **Draw-call budget folklore:** a three.js forum author (high-end hardware) measured ~60,000 draw calls/frame at 60 fps with identical material+geometry, falling to ~3,000 once materials switch. Limiter: CPU submission; single-person measurement. https://discourse.threejs.org/t/shade-webgpu-graphics/66969 **[measured, single source]**
- **Official (non-benchmark) guidance:** R3F docs: keep meshes (draw calls) to "no more than 1000 as the very maximum, and optimally a few hundred or less". This is the number to design against on iGPUs. https://r3f.docs.pmnd.rs/advanced/scaling-performance **[measured -> guidance]**
- **iGPU reality:** no rigorous three.js-on-Iris-Xe scene benchmark exists in public; the nearest signals are (a) a Czech technical thesis benchmarking WebGL vs WebGPU across 4 devices including Intel UHD, finding WebGPU's advantage in draw-call-heavy/buffer-upload scenarios and none in vertex-bound scenes, and (b) opt-in VolumeShader_BM submissions showing Iris Xe running light WebGPU/WebGL raymarching presets at 60-165 fps. The 60-fps hospital budget in the executive answer is **[inferred]** from these plus the per-draw costs above; treat it as a hypothesis to verify with a one-day prototype. **[measured signals -> inferred budget]**
- **Decoder speeds:** meshoptimizer official README: 1-3 GB/s with WASM SIMD (modern desktops); zeux's canonical Draco comparison: Draco decode 19 ms vs meshopt 0.19 ms on a 28K-tri model, 169 vs 1.92 ms on Sponza (184K tris), i7-8650U. Limiter: CPU single-thread decode; 2019-era numbers, still the reference. **[measured]**

## WASM's role for TS/JS 3D

WASM does not replace TS/JS for app logic; it is the escape hatch already built into every asset path, and it neutralizes the classic "JS is slow" objection for this workload:

- **Geometry:** `MeshoptDecoder` is a ~32 KB JS module with inline WASM (scalar + SIMD paths), decodes 1-3 GB/s; Draco ships a 192-286 KB WASM decoder and compresses 20-30% smaller but decodes ~100x slower and skips animation/morph targets. For a hospital (many repeated static assets, occasional animation), meshopt is the default choice. **[measured]**
- **Textures:** KTX2/Basis Universal transcodes to the device's GPU block format and stays compressed in VRAM at ~4-8x less memory than raw RGBA - the only codec that shrinks GPU memory, not just download. **[measured, Khronos/Basis docs via guides below]**
- **Physics (later, if needed):** Havok WASM ships first-party in Babylon; Rapier (Rust->WASM) is the R3F ecosystem standard. Neither touches render performance.
- **What WASM does not fix:** scene-graph bookkeeping in JS (the per-draw cost above) is engine JavaScript, and WASM cannot help there; that is what instancing/batching is for. **[inferred]**

## Docker note

Both libraries are client-side rendering: three.js's official installation manual describes a static site - an HTML file plus a JS bundle, with a `public/` folder whose "files ... are pushed to the website unchanged" (textures, audio, 3D models), built by Vite and served by any static host. The renderer runs in the user's browser against the user's GPU (`WebGPURenderer` uses "a WebGPU backend if the browser supports WebGPU. If not, ... falls backs to a WebGL 2 backend"); nothing GPU-related executes in Node. Babylon.js is the same shape: the engine renders into a `<canvas>` in the browser, and its docs frame deployment as serving JS plus assets. Consequence for the capstone: your Docker container (Next.js) is a plain web server - it serves the built JS bundle and glTF/KTX2 assets, needs no GPU, no graphics drivers in the image, and no change to your existing container beyond adding static asset routes. WASM decoders (Draco/meshopt/KTX2 transcoder) also run client-side, in Web Workers inside the browser. **[measured, official docs]** The one server-side caveat: if you ever wanted server-side rendering of 3D thumbnails you would need headless SwiftShader, which is slow and unnecessary for this app - skip it. **[inferred]**
